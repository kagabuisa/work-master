# Work Master app guide

The account/logout menu closes when you click outside it or press **Escape**. Clicking inside the menu keeps it open so you can use its actions.

This guide describes the current app behavior. Update the relevant section whenever a user-facing workflow, validation rule, permission, or report changes. The implementation and tests remain the source of truth when older documentation disagrees.

Admin has full permission over all voucher types, including sales, purchases, purchase orders, journals, stock entries/reconciliations, and HR vouchers. Admin access includes all creators' vouchers, payments, lists, reports, and exports; saved record restrictions and permission denials do not limit Admin. Actions still follow voucher status, stock, accounting, and dependent-transaction validation rules.

## API authentication and integration access

The `/api/v1` service supports mobile login, rotating sessions, password change, logout, self identity, Admin-managed integration credentials, permitted master-data/stock/invoice/receipt reads, invoice draft creation/editing, separate submission and one-invoice receipt recording. Use the [API guide](api/README.md) for endpoints, field limits and client behavior. Temporary-password mobile users must change their password before protected access. Dedicated integration accounts cannot sign in interactively; administrators manage their role/record restrictions through existing controls and issue/revoke API credentials through the protected API administration endpoints.

Read endpoints enforce customer/supplier categories, all invoice line warehouses, price-list restrictions and Standard ownership/employee exceptions before list counts and pagination. Narrow sales selectors expose permitted invoicers or receiving accounts without general employee/account access. Individual receipt reads apply account restrictions while invoice header totals keep their existing meaning. Website and API invoices share the calculation rules described under Vouchers below. Multiple-invoice API allocation is deferred.

API clients save a draft with `POST /invoices`, edit a draft with `POST /invoices/{id}`, submit with `POST /invoices/{id}/submit` and record a receipt with `POST /invoices/{id}/payments`, relative to `/api/v1`. Each requires a separate stable `Idempotency-Key`, JSON and current action/record permissions. Drafts accept 1–200 lines in one header warehouse, decimal-string quantities (three places), selling rates (six places), and adjustments/receipts (two input places, rounded to whole UGX). Client names, totals and embedded receipts are rejected. New and edited API drafts must pass current/historical stock and reconciliation cut-off checks before saving, regardless of the optional legacy `check_stock` flag. Drafts do not reserve stock; failed submission retains the draft. Receiving-account eligibility and the existing balance calculation, including qualifying journal allocations, govern receipts; the account derives payment method.

API reliability includes transaction-local reference/permission checks, stable retry identity, deterministic stock locking and audit resource links on replay. Identical retries return the original committed result for seven days; changed payloads conflict. After expiry, reconcile a draft rather than blindly recreating it. Receipts additionally require `external_source` and `external_reference` and remain protected across new keys, expiry and credential rotation. Permanent references remain reserved after website cancellation and never reactivate a receipt. Existing website payments retain their own generated journal references and workflows. API draft editing is supported with current Edit permission; cancellation uses the website. Local automated verification is complete, while real-client staging acceptance and operational launch checks remain open.

Operators can temporarily disable API access without disabling the website. During containment, clients receive 503 `api_disabled` and should retain their original retry keys/references rather than recreating financial operations. The switch does not undo earlier commits or change permissions. Request IDs and redacted operational telemetry help reconcile incidents. See the [operations runbook](api/operations.md) for containment, credential recovery, backups and rollout; real-client staging and production acceptance remain pending.

For synthetic practice and deployment checks, the [local staging environment](api/local-staging.md) is available at `https://localhost:3443` after trusting its local CA. Its Admin/mobile passwords and integration credentials are generated privately and its database is separate from company data. The restricted sales account can use only staging records assigned to it. Scripted checks create drafts, submit invoices, record receipts and verify retries/website visibility; actual phone and external-client acceptance remains pending.

## Transaction maintenance

Administrators can open **Settings → Maintenance → Reset transactions**. The screen lists the current counts of records to remove. **Accounting and stock only — retain HR** removes sales, purchases, purchase orders, payments, journals, stock movements and balances, reconciliation attachments, daily activity records, and non-HR ledger entries. HR attendance, leave, payroll, employee money, and their ledger entries remain, so HR-related financial balances remain. **All transactions, including HR** also removes HR transactions and all ledger entries; stock and account balances then become zero.

Both scopes preserve master lists, users, roles and permissions, company/display/accounting settings, employee profiles, pay plans, leave types, holidays, and project files. Voucher numbering continues rather than reusing old numbers. Reset history and existing API audit records remain.

Select the scope and **Create verified backup**. This backs up the full database and persistent files to private storage and checks that the archives are readable and unchanged. Download a copy and keep it outside the app. Database operations pause while the backup is prepared or a reset is running. A backup is eligible for reset for 15 minutes; changes to business records or files require a new backup. Enter your current administrator password and type **RESET TRANSACTIONS** exactly to reset. The reset rechecks the backup and removes linked records together; a failure rolls back the removal. Successful resets record the administrator, time, scope, backup, and removed counts.

After a reset, all website and mobile sessions end and integration tokens are revoked. Sign in again and replace integration tokens before reconnecting clients. After a full reset, enter opening stock and opening balances before resuming business. Recovery of removed history requires restoring the backup.

## Vouchers

Sales invoice quantities support three decimal places and selling rates support six. Rates retain their precision in item selection, editing, invoice details, print and invoice reports. Each quantity × rate line amount is calculated using decimal arithmetic and rounded to whole UGX; halves round away from zero. The subtotal sums those rounded lines. Discount and tax are individually rounded to whole UGX before calculating the total. The applied discount cannot exceed the subtotal; tax is added after that cap. Preview, saving, and cash-sale receipts use the same calculation. A cash sale must receive exactly its saved positive total; otherwise the whole submission is rolled back. Existing saved invoice amounts are preserved when viewing them; editing a draft recalculates it under these rules.

Stock issues use a proportion of the locked remaining stock value, rather than multiplying by a rounded average rate. Issuing all remaining quantity consumes all its value. Transfers carry the exact issued value into the destination, and cancellations reverse the original saved movement values. Invoice costs and inventory accounting use these posted movement amounts. Displayed average rates are rounded reference values. A reversal that would leave value without quantity is rejected for review and an approved correction. Previously posted history is retained.

If historical stock has zero quantity but a nonzero value, a reviewed zero physical count posts a separate value correction that clears the residual. It preserves the original movement history. Controlled inventory requires the usual count review and approval before submission. Reversals that would create negative stock value are rejected.

Posting dates cannot be later than today in **Africa/Kampala**, including for Admin and API requests. This applies when submitting sales and purchase invoices, purchase orders, journals, stock entries/reconciliations, attendance, Employee Money and payroll, and when recording receipts, payments or dated reversals. Future-dated drafts may be prepared but cannot be submitted until their posting date arrives. Due dates, planned delivery dates, leave dates and other planning dates may remain in the future. Existing postings are not rewritten.

New vouchers default to the current Kampala date and time. Date and time remain editable on editable forms, subject to the existing voucher rules. Sales invoice accounting and its generated journal retain the invoice’s selected posting date. With controlled inventory active, physical stock movements still use the server-assigned movement time; changing the invoice date does not backdate stock or reopen closed stock history.

Voucher fields use one identifier per master record: **Item Code**, **Customer ID**, and **Supplier ID**; **Employee Name**, **Cost Center Name**, and **Account Name**. Pickers and item rows follow the same rule, without repeating IDs beside names or showing a second Item Name column. Searches still accept names and codes where supported. IDs remain stored internally for permissions, references, and saving.

Employee, cost center, and account names must be unique, including inactive records. Names differing only in capitalization or surrounding spaces count as duplicates; creating or editing a duplicate is rejected.

### Sales invoice details

In the Item Code search results, clicking or tabbing into **Qty** clears its value so you can type the quantity directly. Enter a positive quantity, then press **Enter** or select **Add**. Selecting **Add** without entering the Qty field keeps the default quantity of 1.

Before controlled-inventory activation, the item search results and **Stock as of posting** column show warehouse quantities at the selected invoice date and time. With controls active, forms show **Current stock preview** and server submission assigns the actual stock timestamp. Added and saved draft lines refresh when you add items, remove lines, edit quantities, change the posting date/time, or return to the window. The column also shows a lower **available** quantity where later transactions reserve stock. Stock figures refresh together: invoices with up to 200 distinct item/warehouse pairs use one balance request, and larger invoices refresh in bounded batches. Repeated pairs share the same result. Stock refreshes share the app’s read capacity limits to preserve posting capacity. Loading and lookup failures are shown explicitly; failed or missing results show Unavailable rather than zero, and superseded responses cannot replace newer figures. Submission always checks stock again. These figures describe posted warehouse stock before the unsaved invoice, so entering a quantity does not deduct it from the displayed warehouse balance.

Before controlled-inventory activation, sales invoice submission checks stock at the saved invoice date and time. With controls active, submission checks both current stock and historical availability at the selected posting date/time. It also rejects ordinary postings at or before a warehouse’s permanent reconciliation cut-off. The physical movement still uses the current controlled timestamp. Later receipts or reconciliations cannot supply a backdated sale. A sale is also rejected if it would leave negative stock during later recorded transactions. Repeated lines share the available quantity; failed submission leaves the draft unposted. For example, if yesterday’s stock was 10 and today’s reconciliation increases it to 100, an invoice dated yesterday cannot sell more than 10.

- **Save** checks the combined quantity for each item/warehouse against current stock, stock available at the selected posting date/time, later stock minima, and permanent reconciliation cut-offs before creating or updating the draft. A rejected save creates no invoice and leaves an existing saved draft unchanged; the form retains your attempted values for correction. Saving does not reserve or deduct stock. Review and submit the saved invoice to post it; submission checks availability again.
- Customer and item suggestions support **Up/Down** to focus results, **Enter** to select, and **Escape** to close. Item quantities remain editable before adding. Screen readers receive result counts and loading/error messages.
- At the first or last list page, unavailable Previous/Next controls are disabled and skipped by keyboard navigation.

- New invoices start with the current Kampala **Posting Date** and **Posting Time**; both can be changed. The stored `invoice_date` field is the posting date used by the invoice and ledger workflows. **Due Date** is separate.
- New invoices select the user's assigned warehouse and retail price list when those choices are permitted and available. Without an assigned retail list, the form selects **Retail Pricelist** when it is active and permitted. The user can change either field before saving. **Ext Invoice** holds an optional outside invoice reference.
- The full view and print view show the invoice number directly below the **Sales Invoice** or **Cash Sales Invoice** title. The drawer shows the number once in its top link bar.
- Sales invoice lists and reports label the date as a posting date. The sales invoice report supports filters, selectable columns, and CSV download.
- Price lists and item prices supply suggested rates. Existing invoice lines retain their saved rates.
- Duplicating an invoice fills each copied line's Stock column with the current balance in the selected warehouse when the duplicate form opens. The balance is checked again when the invoice is saved or submitted.

### Stock reconciliation count sheets

Submitting a reconciliation keeps every counted item on the voucher, including items that match the book balance. Only items with a quantity or stock-value difference are posted to the stock ledger. Matching items show zero differences on the submitted voucher. A count with no differences can be submitted and cancelled without stock-ledger or accounting entries. Differences are checked against the current warehouse balance at submission; existing historical ledger rows remain unchanged.

Choose a warehouse on a new reconciliation or open **Edit count** on a draft. Select **Download Excel template** to download an `.xlsx` workbook with that warehouse's stocked items, book quantities, and blank **Counted Qty** cells. A saved voucher's items are included even if their current stock is zero. Spare rows allow other active item codes to be counted. A read-only voucher also offers the template download. Downloaded filenames include the reconciliation number and warehouse, for example `REC-000001-Main-Store-count-sheet.xlsx`; unsaved vouchers use `new-reconciliation` in place of the number.

Fill **Counted Qty** with the physical count, including **0** for zero stock, using up to three decimal places. Leave uncounted rows blank; blank quantities are ignored rather than treated as zero. Keep **Warehouse** and **Item Code** intact and use one row per item. The workbook includes an Instructions sheet.

Select **Upload count sheet** on a new or editable draft voucher and choose the completed `.xlsx` file (up to 5 MB and 5,000 item rows). Matching item counts are replaced and additional valid items are added. Rows omitted from the upload keep their current form counts. Unknown or inactive items, duplicate counted items, wrong warehouses, negative or invalid quantities, and formula quantities reject the upload without changing the form. Item names, current book quantities, and valuation rates come from the app; workbook book quantities and names are not trusted as current data, and rates are not imported. Existing valuation-rate permissions still apply.

Uploading fills the form without saving or posting. Review the count and value differences, then **Save draft** or **Submit reconciliation**. Submitted and cancelled vouchers cannot receive uploads. Submission checks the current stock balance and applies the existing reconciliation rules.

Scanned physical stock sheets and spreadsheet files can be attached separately under **Scanned stock sheets** after saving the voucher. Users with Stock Entry Edit can attach or remove supporting PDF, JPG, PNG, CSV, and Excel (.xls/.xlsx) files on saved draft, submitted, or cancelled reconciliations. Upload up to three files at a time, no larger than 10 MB each. A “request is too large” (413) response for a smaller file indicates that the server proxy upload limit needs to be increased. The list shows file name, size, uploader, and upload time; select a file name to download it. Uploaded scans are retained until removed or the voucher is deleted. Attaching or removing scans does not change the count, voucher status, stock ledger, or accounting entries. These attachments are supporting evidence; use **Upload count sheet** above to import Excel quantities.

### Paying multiple purchase invoices in one journal

Journal main inputs align within each responsive grid row, with selected reference chips displayed below the field grid so they do not shift the References input. The journal form keeps References and account rows compact; the reference-selection and partial-payment instructions are provided here in the guide.

Select **Supplier** and the supplier's **Party ID**, then choose one or more outstanding purchase invoices from **References**. Each selection adds a separate **Accounts Payable** debit row with its invoice reference and outstanding balance. Repeated selection of the same invoice does not add another row. Edit the debit amounts for partial payments. Add a separate bank or cash credit row for the combined payment, leaving its Reference blank. You can also select an invoice directly in a row's Reference field. Removing a selected reference removes its rows; changing the party clears referenced rows to prevent allocations to the previous party.

The invoice picker lists submitted invoices with outstanding balances for the selected supplier. Saving a draft does not pay the invoices. Posting creates one payment allocation per invoice and updates each invoice's paid amount and status. Repeated rows for one invoice are added together. Payments cannot exceed the invoice's outstanding balance or precede its posting date. Cancel the journal to reverse all its allocations and restore invoice balances; its linked allocations cannot be cancelled individually from an invoice. For **Customer** parties, select multiple outstanding sales invoices in **References** to add separate **Accounts Receivable** credit rows. Add a bank or cash debit row for the combined receipt. Posting applies each row to its invoice; cancellation reverses those allocations. Customer invoice lists, payment details, debtor statements, and reports include these receipts. Existing journals with a single header reference remain supported. For **Employee** parties, references with permitted employee ledger rows copy those account rows and amounts into the form. Review these copied rows and balance the journal before posting; employee references do not allocate invoice payments.

### Journal account rules

- Saved journal details and the voucher drawer show the saved **Cost Center** and all distinct **References** from the header and account rows. Individual references also remain beside their account rows.
- In an editable journal, use the **↑** and **↓** buttons under **Actions** to rearrange account rows. Each move keeps the account, amounts, reference, and line remarks together. Saving preserves the displayed row order.
- Voucher forms keep posting date and time collapsed in the main details row. Select **Edit date / time** to open the fields in a floating panel without moving the main inputs (above the bottom edge on small screens); read-only journals and stock entries offer **View date / time**. New invoices, purchases, purchase orders, journals, stock entries, and stock reconciliations default to the current Kampala date and time. Saved vouchers keep their existing values when reopened. Click outside the floating date/time panel or press Escape to close it; entered values are retained. Collapsed fields are still saved, and invalid fields open automatically for correction.
- Payment and HR voucher forms offer a compact **Edit payment date** or **Edit posting date** control and default to today's date. Payroll also defaults to today; choose a completed payroll month or edit the posting date to meet the month-end rule. Due dates, payroll month selection, attendance dates, and report filters remain visible.
- The journal's **Remarks** field appears below the account rows and totals, just above the form's action buttons. Individual **Line Remarks** remain beside their account rows.
- Every amount-bearing line needs an account. A single line cannot contain both a debit and a credit.
- Total debits must equal total credits.
- An account may appear on multiple debit lines or multiple credit lines, but it cannot appear on **both** sides of the same journal. The form shows this conflict, and the server rejects it when saving or posting. Submitting an older draft applies the same rule.

## Historical reports and simultaneous use

Controlled inventory checks each posting event’s stock movements against its invoice and accounting before the submission commits. These checks use a posting-event lookup index, so the event check can find the current voucher’s movements without scanning the full stock ledger. Submission still waits for validation and commit; saved drafts do not post stock or accounting.


The General Ledger **Party** filter defaults to **All related voucher postings**, so selecting a customer includes their invoice revenue postings along with the other accounting lines. It has two explicit scopes. **Party entries** matches the party ID or name recorded on each posting. **All related voucher postings** includes the other accessible lines of a matching voucher, including Sales Income, COGS, Inventory, tax, and bank accounts even when their party field is blank. Account, Voucher, date, Search, and access restrictions still apply. **View posting** beside a voucher opens its exact voucher type and ID and clears the other report filters, so you can reconcile all accessible debit and credit lines without mixing documents that happen to have the same numeric ID. Account and ownership permissions still apply; a restricted posting view may omit lines.

The ledger uses compact totals with an emphasized Net Balance, a single-line customer receivable summary with a status pill and highlighted amount, and a dense transaction table. Opening rows and account headings are subtly tinted; View posting remains a compact link beside each voucher. Section help icons provide additional guidance.

**Filtered debits** and **Filtered credits** describe only the selected period postings, so the totals may differ. **Net Balance** equals the sum of matching opening balances plus filtered period debits minus filtered period credits. It includes opening history on every page and in downloads. It combines the selected GL accounts and is separate from customer outstanding receivables. Voucher posting reconciliation compares period debit and credit totals, excluding opening balances. **Account Running Balance** is calculated separately for each GL account, including opening history. Choose **Group by → GL account** to order postings by account and show a full-period summary of opening, period debit, period credit, and closing for each account. Closing equals opening plus debit minus credit.

Customer and supplier summaries use matching, evenly spaced status strips: heading, **Customer** or **Supplier**, **Payment position**, and right-aligned **Balance (UGX)**. Small screens place the party name above the position and amount. Payment position remains visible: positive customer balances show **Outstanding receivable**, negative balances show **Credit balance**, and zero shows **Settled**. Supplier balances use Accounts Payable credit minus debit: positive shows **Outstanding payable**, negative shows **Supplier advance**, and zero shows **Settled**.

When Party matches a customer or supplier, the corresponding **Customer receivables** or **Supplier payables** strip shows the control-account balance through **To**, or across all dates if To is blank. It retains Party and access restrictions but ignores From, Account, Search, Voucher, and Party scope. Customer and supplier positions remain separate even when their IDs or names match. These balances are distinct from the net across bank, sales, inventory and other accounts. **Narration** shows the saved posting remarks. Posting details for cash receipts, payment journals and journal entries show saved **Invoice allocations** from receivable/payable source lines, using line references or the journal reference when the line reference is blank. Source allocations are supporting details, not additional postings; cancellation rows reverse their accounting effect.

General Ledger begins with an **Opening balance** row for each matching account. It includes matching postings before **From**; with no From date, opening is zero. Opening rows repeat at the top of each page and are excluded from transaction counts and period debit/credit totals. Running balances include opening history and earlier pages, separately per account. Accounts with historical activity remain visible in opening rows even when there are no period transactions. Positive balances are debit and negative balances are credit. Account, Party, Search, Voucher, To, and access restrictions apply to opening history too. Opening balances and period totals are calculated together to reduce repeated database work. The page, matching count, and debit/credit totals come from one saved-data snapshot, so a transaction posted while the report loads does not mix newer rows with older totals. Entries before a page are calculated separately for earlier dates and earlier entries on the same date, preserving running balances when many transactions share a date or a transaction is backdated. Refresh or Apply again to include later postings. General Ledger and Trial Balance require valid dates with **From** on or before **To**. Trial Balance opening balances include postings before From; narrowing the period does not discard opening history.

Invoice lists use indexed creator and employee-assignment lookups for restricted users. A document matching both routes appears once, and other category and warehouse restrictions still apply. Before accepting an invoice payment, the app finds manual customer journal allocations by their header and individual line references using indexed lookups. Matching allocations are counted once; cancelled journals and journals already linked to saved invoice payments do not reduce the available balance again. Payments still cannot exceed the remaining balance. Invoice details load the header, items and payment history from one saved-data snapshot, so a concurrent edit cannot mix versions; refresh to see later changes. Warehouse and customer-category visibility checks read only the fields needed to enforce those restrictions. Invoice details look up payment journals by the invoice reference, including individual line references; cancelled journal payments remain visible in payment history without increasing the paid amount. Lists/searches and heavy reports have separate waiting queues. Viewing requests share a database connection limit so they leave capacity available for saving and posting. If a queue is full or its waiting limit expires, retry the view shortly. Invoice lists and text searches look up payment journals by the displayed invoice references, including references entered on individual journal lines. Linked payments are counted once; cancelled journals are excluded. Invoice and journal text searches retain case-insensitive per-field matching and `%` wildcards. Searches by numeric amounts, dates, and invoice payment status remain available. Identical simultaneous report requests can share their database work only when their filters and access restrictions match; completed financial report results are not cached. Requests already waiting for the same report may share one execution that starts after the latest posting; a new request never joins a report snapshot that started before its latest committed changes. The historical warehouse and ledger voucher-type choices refresh within 30 seconds. Warehouse choices use indexed lookups and retain warehouse names used on older invoices even when they are absent from current master records; the user’s warehouse restrictions still apply. Transaction resets clear these temporary choices.

### Payroll cancellation and accounting

Cancel active salary payments before cancelling payroll. A posted cancellation requires a date no earlier than payroll posting and a reason. It reverses the accrual, restores employee recovery balances, preserves the original records, and permits a replacement payroll for the employee/month. Salary payments and employee-money payments have their own reversal actions and dates. Posted records cannot be edited.

HR accounting appears in General Ledger and financial totals. New HR transaction details in General Ledger and its exports require the matching Payroll or Employee Money Read permission, plus applicable employee/cost-center/account scopes. ### Controlled warehouse counts and permanent inventory closure

After operational activation, open **Stock → Stock Reconciliation → Counts and warehouse closure**. The warehouse table shows open/frozen status and its permanent closing timestamp in Kampala time. Legacy reconciliations do not automatically close history.

1. Stop all physical receipts, dispatches and transfers. Submit every preceding physical movement and review pending drafts. Future movements may remain drafts. The readiness confirmation records the responsible operator's attestation; the app cannot verify physical movement outside the system.
2. Select **Start count and freeze warehouse**. The app waits for preceding postings, records the database cut-off and captures warehouse book quantities, values and rates. Ordinary posting affecting this warehouse, including either side of a transfer, is blocked while the count is active.
3. Enter explicit physical quantities, including zero. Blank quantities are incomplete. Explain discrepancies and provide positive valuation rates for gains. Add found item codes where needed. **Download count sheet** uses the frozen snapshot; importing that session's current Excel revision saves counts without approving or posting. Stale/wrong-session sheets are rejected. Blank imported cells leave existing lines unchanged and never automatically complete uncounted items.
4. Save, request review, and obtain approval. Non-administrators need another authorized person to approve; administrators may approve their own reconciliation. Changing supporting sheets/photos invalidates approval and returns the count to counting with a new revision. A non-administrator who entered counts or changed evidence cannot approve that count. After a review rejection, recount and request review again.
5. Submit the approved revision. Reconciliation stock, inventory accounting, the permanent warehouse cut-off and release of the freeze commit together. A matching count with no adjustments still closes the warehouse. The cut-off covers every item, including items not listed and future items.

A failed submission leaves the warehouse frozen and creates no permanent closure. Retry after resolving the error, or use **Abandon count** with a reason. Abandonment releases the freeze without closing history and permanently prevents reuse of that session. If physical movement occurs during counting, abandon and restart the physical process. A submitted count cannot be reopened or cancelled.

When controlled inventory is active, **all new inventory movements use the server's submission timestamp**. Sales invoice dates govern invoice accounting; purchase and stock-entry dates remain document dates under inventory controls. Entered posting times do not backdate inventory. Forms show the current stock preview and warehouse restrictions. Actual inventory times appear in the Stock Ledger; associated inventory GL postings use the same Kampala posting date except sales invoices, whose accounting and generated journal retain the selected invoice posting date. The current stock preview is not permission to consume later receipts on an earlier posting date. Submission also checks historical availability and protects later stock balances. All ordinary sales, purchase and stock-entry document dates/times must be after every affected warehouse’s permanent cut-off, including zero-difference counts and items omitted from or created after the count. Omitted historical movements use the approved current-period correction workflow. Minute-only inputs for the current submission minute use the submission instant for stock/closure checks, allowing normal posting immediately after a count or receipt; explicit earlier minutes and precise timestamps retain their selected time. Submission always rechecks warehouse state and stock. A saved draft does not reserve an old movement timestamp.

### Current-period inventory corrections

Open **Inventory corrections** from the warehouse count or stock-entry list. Closed original vouchers remain unchanged; do not recreate their stock movement with a redated invoice.

- **Already absorbed in closed count:** link a submitted count, item and signed discrepancy quantity, provide a unique original source reference, detailed evidence/reason, and balanced financial reclassification lines. This records a financial/documentary correction without issuing or receiving stock again. Available allocations are conservatively limited to the count item's signed net discrepancy, including quantities already reserved by prepared corrections. Mixed historical events that cannot be evidenced within that net discrepancy are not automatically inferred or absorbed.
- **Actual new physical movement:** enter a signed quantity and incoming valuation rate. Leaving financial lines empty uses the standard stock adjustment accounts. Explicit financial lines must balance and their inventory net must match the physical stock value.

A different authorized reviewer approves the exact prepared correction before posting. Receivable/payable lines require a customer/supplier identity; use the original source reference and evidence to explain any reclassification already represented by reconciliation gain/loss. Absorbed corrections cannot change the inventory account net a second time. Corrections are separate COR records and General Ledger adjustments, not new sales or purchase invoices; invoice payment/status workflows do not attach to them. Review party statements and use the existing journal workflow for subsequent financial settlements.

Prepared correction quantities and financial lines are immutable through the runtime. An unposted draft/approved correction may be explicitly abandoned with a reason; this releases its reserved absorbed quantity and permits a replacement using the same source reference. Posted references remain permanently reserved. For a multi-item original, use a distinct document-and-line reference for each item correction and allocate financial amounts without repeating the full document total. Submitted corrections and their audit records remain in history. Correct an erroneous physical count through a later controlled count rather than undoing its original closure. Transaction resets are disabled after controlled inventory activation; verified backups remain available. The inventory account mapping is fixed while controls are active. Manual journals cannot post to the inventory account: use controlled stock entries or reviewed inventory corrections so stock and accounting commit together.
